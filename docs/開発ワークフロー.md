# 開発ワークフロー（正本）

TAKUMI-CMO の改修・拡張はこの規約に従う。目的は **回帰ゼロで無双マーケティングエンジンを育てる**こと。
Cowork の実行仕様は [cowork-runtime.md](cowork-runtime.md)、ドメインの言葉は [domain-model.md](domain-model.md) が正本。

## 0. 原則

1. **技術負債を作らない** — 中途半端なリネーム・孤児参照・スタブ・stale docs を残さない。不変条件は機械（lint/テスト）に落とす。
2. **日本語を原則とする（コードを除く）** — ドキュメント・手順書・コミットメッセージ・PR・報告は日本語。コード（識別子）は英語でよいが、集約・値オブジェクトの命名は [domain-model.md](domain-model.md) のユビキタス言語と1対1で対応させる。
3. **Cowork 前提** — 安全ゲートの機械強制は Cowork 実機でのみ確証できる。ローカルでの hook 配線は**環境依存で振れる**（2026-07-24 は未配線 / 2026-07-25 は配線されていた → escalations E4）ため、「ローカルだから効かない」と決め打たず**毎ラン発火を実測する**。設計は常に「hook が沈黙しても壊れない」多層防御を前提に置く（E5）。

## 0b. 外部サービスの仕様を正本に書くときの規律（2026-07-25 追加）

`skills/` のスキルや `docs/` の正本に**外部サービス（Google・Microsoft 等）の仕様を書くときは、一次情報を当たること。**
検索結果の要約や解説記事だけを根拠に規範を書かない。実際、GA4/GTM/GSC のスキル初版は検索要約のみで書かれており、
一次情報を当てたところ **DOM要素変数のブロック対象を誤記**、**既定チャネルに存在しないものを「追加された」と記載**、
**公式に記載のない措置（データ全削除）を断定**、という3つの誤りが出た。
続けて日本の法令（個人情報保護委員会・総務省）を当てたところ、**日本法の水準を EU 並みに見積もる過剰な規範**も出た
（Cookie 利用に同意が要るかのような記述、要配慮個人情報でないものを収集禁止扱い）。

**誤りは「厳しすぎる方向」にも出る。** 規範が過剰だと監査が不要な NO-GO を出し、運用が回らなくなる。
法域ごとの水準（EU / 日本）と、契約上の拘束（Google 規約）を**混ぜて書かない**。前者は緩くても後者は緩まない。

- **一次情報 = 提供元の公式ドキュメント**（`developers.google.com` / `support.google.com` 等）。WebFetch で本文を取得して読む
- **確認できたもの／できなかったものを分けて書く。** スキル末尾の出典を **【一次情報・確認済み】** と **【二次情報のみ・未確認】** の2節に分ける
- **未確認の記述は「未確認」と明示し、実機で確認する手順に落とす。** 断定形で書かない
- **数値（シェア・比率・改善率）は特に危ない。** 出所を辿れない数値を**設計判断の根拠にしない**。
  判断そのものが数値なしで成立するなら、数値を引用せず理屈で書く
- **反証も探す。** 肯定する検索だけを回すと、二次情報の合意がそのまま事実になる
- 検索ツールが US 中心の場合、**日本の法令・実務は構造的に取りこぼす**。日本固有の論点は日本語の一次情報（省庁・公式ヘルプ日本語版）を当たる

**この規律は合議（`docs/parts/pre-setup-council.md`）の前提でもある。** 合議に参加するエージェントは
`skills/` を正本として読むため、**正本が二次情報のままだと合議の結論も同じ弱さを引き継ぐ**（循環参照）。

### 0b-2. 「外部の事実」と「社内の型」を混ぜない（2026-07-26 追加）

上の規律は**外部の事実を引用するとき**の話だった。しかしスキルの中身の多くは
**本プロダクトの型・運用経験**であり、外部の一次情報ではない。**この2つが同じ書き方で
並んでいると、読み手（AI を含む）は同じ強さの事実として受け取る。**

実際、2026-07-26 の全体CHECK で次が出た:

- `skills/copywriting` の「記事タイトルは**検索結果の表示上限に合わせて** 32文字以内」——
  **Google はタイトルの文字数上限を規定していない**（「`<title>` の長さに制限はないが、
  検索結果では必要に応じて、通常はデバイス幅に合わせて切り詰められる」）。
  社内の目安に**外部仕様という衣を着せていた**
- `skills/web-design/resources/lp-cro.md` は本文で「**CVR最適化の数値根拠**」と位置づけられ、
  改善率（+104% / +46% / +35〜40% / 13.5% vs 10.5%）が5つ並ぶ。**出典は1つも無かった。**
  §0b が「特に危ない」と名指しした種類の数値が、「根拠」という名前で置かれていた

**ラベルは5種類。スキル末尾の `## 出典` に、使ったものを必ず書く:**

| ラベル | 意味 |
|---|---|
| **【一次情報・確認済み】** | 提供元の公式文書を本文取得して確認した |
| **【一次情報・出所は特定済み／原文は未取得（要確認）】** | どこが出しているかは分かるが原文を読めていない |
| **【二次情報・原典未取得】** | 解説記事・要約が根拠。**成果物に数値として引用しない** |
| **【未確認】** | 根拠を辿れていない。断定形で書かない |
| **【社内基準】** | 外部の事実ではなく、本プロダクトの型・運用経験。**目安であって引用可能な根拠ではない** |

**外部出典がゼロのスキルは「出典なし」で済ませず、【社内基準】と明記する。**
空欄と「無い」は違う——空欄は**書き忘れと区別がつかない**。

**この規律は `skills/*/SKILL.md` だけでなく、その配下（`resources/` 等）にも同じく効く。**
下位ファイルは本文から「必読」で開かれる以上、正本と同じ強さで読まれる。
機械検査は lint #24（`## 出典` 節の存在と、ラベルが1つ以上あること）。

## 1. 原子的ブランチ & マージ戦略（回帰防止）

- `main` は常に緑（CI 全通過）。**`main` へ直接コミットしない。**
- 作業単位（フェーズ／独立した1つの変更）ごとに feature ブランチを切る: `phase/<名>` または `fix/<名>`（ブランチ名は ASCII）。
- ブランチを push → **PR を作成**（`pull_request` トリガで CI が回る）→ **CI 全緑を確認** → `main` へマージ（`gh pr merge --merge`）。
- 1 PR = 1 つの意味的にまとまった変更（原子的）。lint / テスト / test-hooks / shellcheck が赤いまま PR をマージしない。
- マージ後に feature ブランチは削除。次フェーズは `main` から新ブランチ。

## 2. TDD（テストファースト）

**テストを先に書き、赤を確認してから実装し、緑にする。**

- **ドメインコード**（`takumi/` Python パッケージ）: `tests/` に unittest（stdlib・依存追加なし）を先に書く → `python3 -m unittest discover -s tests` で red → 実装 → green。
- **hook（bash）**: 新ゲートは `scripts/test-hooks.sh` に「denyされるべき入力」「素通しすべき入力」のケースを**先に**追加 → red → hook 実装 → `bash scripts/test-hooks.sh` で ALL PASS。
- **Cowork 統合**（hook 配線・コマンド経路・エージェント起動・ブランド分離など機械テスト不能な項目）: 実行可能な仕様＝**検証項目（V番号）を先に** `procedures/takumi-verify.md` に追加してから機能を作る。これが Tier 2 の TDD。

## 3. オブジェクト型 DDD

- ドメインを**集約（Aggregate）・エンティティ・値オブジェクト**でモデル化する（[domain-model.md](domain-model.md)）。中心は **Brand 集約**（マルチブランドの分離単位＝`knowledge/brands/<slug>/`）。
- **ランタイム（Cowork が読むもの）とドメインモデル（dev-side コード）を分ける**:
  - ランタイム = markdown（commands/procedures）+ bash（hooks）+ templates。Cowork 上で人＝AI が読んで実行する。
  - ドメインモデル = `takumi/domain/` の Python。集約の不変条件（ブランド slug の一意性・KPIツリーの整合・区画パスの正当性）をコードで表現する。
  - **両者を繋ぐのが `takumi/workspace.py`**: `python3 scripts/lint.py --workspace <path>` でワークスペースの `knowledge/brands/**` をドメインモデルで検証する（検証するファイルと形は [domain-model.md](domain-model.md) の「ワークスペース検証」が正本。Tier 2 の V49）。`knowledge/` が無ければ何も起きないので CI には影響しない。
- 集約の境界＝**Brand Isolation Guard（hook）の境界**。「別ブランド区画への書き込み禁止」はドメインの不変条件であり、hook で機械強制する。

## 4. 二層検証（Tier 1 / Tier 2）

| 層 | いつ | どこで | 何を | 手段 |
|---|---|---|---|---|
| **Tier 1** | 毎コミット | ローカル / CI | 参照整合・ドメイン不変条件・hookロジック・シェル健全性 | `lint.py` / `python3 -m unittest` / `test-hooks.sh` / shellcheck |
| **Tier 2** | フェーズ節目 | **Cowork 実機**（cloud 基本。ローカルは hooks 配線が環境依存 → E4） | hook実配線・コマンド経路・エージェント起動・ブランド分離・ブラウザ実操作 | `/匠検証`（takumi-verify）を実タスク形式で実行 → PASS/FAIL を貼り戻す。**ゲート項目は発火を実測して判定**（通ってしまったら PASS にせず SKIP(未配線を実測)） |

- **各検証項目は Tier を明示する**（`procedures/takumi-verify.md`）。Tier 1 で緑でも、hook 配線・経路・分離は Tier 2 でしか確証できない — 「Tier 1 が緑＝Cowork で動く」と誤認しない。
- Tier 2 が要るのは hook / コマンド / エージェント / ブランド境界が変わったフェーズ（[cowork-runtime.md](cowork-runtime.md) §6）。docのみの変更は Tier 1 で足りる。

## 5. CI（GitHub Actions・push[main] と全 PR で発火）

`.github/workflows/ci.yml` が回す（強化していく）:

1. `lint`: `python3 scripts/lint.py` → `lint: OK`（参照整合・frontmatter・JSON・台帳・version・delve-残骸禁止・**旧プラグイン名由来の識別子の混入禁止（#10）**・**docs/parts/ と index.md の双方向突合（#14）**・ブランド区画スキーマ）
2. `tests`: `python3 -m unittest discover -s tests -v` → ドメインモデル（DDD 集約）の単体テスト全緑
3. `hooks`: `shellcheck --severity=error hooks/scripts/*.sh scripts/*.sh` + `bash scripts/test-hooks.sh` → `ALL PASS`

CI が赤い PR はマージ不可。**新しい機械チェックを足したら、それが守る不変条件をこの表に1行追記する。**

## 6. フェーズ完了の定義（Definition of Done）

- [ ] Tier 1 全緑（lint / unittest / test-hooks / shellcheck）
- [ ] 変更した不変条件に対するテスト（TDD で先に書いたもの）が存在し緑
- [ ] 台帳（`docs/command-registry.md`）と実体が双方向一致（lint が保証）
- [ ] PR の CI 全緑 → `main` にマージ
- [ ] hook/コマンド/エージェント/ブランド境界を変えたフェーズは、対応する Tier 2 検証項目（V番号）を追加済み（実機実行はユーザーに依頼）

## 7. 配布（リリース）手順

このリポジトリ自体が marketplace（`.claude-plugin/marketplace.json`）。**タグやビルド成果物はなく、`main` の内容がそのまま配布物**になる。したがって「main にマージした時点で配布済み」— リリースの実体は **version の繰り上げ**である。

### リリースチェックリスト

- [ ] **1. Tier 1 全緑** — `python3 scripts/lint.py` / `python3 -m unittest discover -s tests -t .` / `bash scripts/test-hooks.sh` / `shellcheck --severity=error hooks/scripts/*.sh scripts/*.sh`
- [ ] **2. version を繰り上げる** — `.claude-plugin/plugin.json` と `.claude-plugin/marketplace.json` の**両方**（不一致は lint #1 が落とす）。
      **Cowork は version フィールドの変化でしか更新を検知しない**（TESTING.md T0b）ため、配布したい変更があるなら必ず上げる
- [ ] **3. README のコマンド表**が実体と一致（README は利用者向け。**構成物のカウントやフェーズ進捗は書かない** —
      すぐ陳腐化して負債になるため、台帳は `docs/command-registry.md`、進捗は git 履歴と `TESTING.md` を正とする）
- [ ] **4. PR → CI 全緑 → `main` へマージ**（`gh pr merge --merge --delete-branch`）
- [ ] **5. Tier 2 実機ゲート（人間が実行・自動化不可）** — cloud Cowork で marketplace を更新し、
      cloud Cowork で **`/匠検証 full`** と言うだけ（**ファイルの配置もコピーも不要**）→ **FAIL 0**。
      結果（PASS/FAIL/SKIP 件数・FAIL 詳細・実行環境）を `TESTING.md` に実機ランとして追記し、
      **`TESTING.md` の `<!-- tier2-verified: <version> -->` マーカーを更新する**。
      マーカーが現行 version と食い違う間、`scripts/lint.py` は毎回 **WARN** を出し続ける
      （CI は落とさない — 実機検証は人間にしかできないため。ただし未実施が黙って積み上がる状態は作らない）
- [ ] **6. FAIL が出たら version を戻さず修正版で繰り上げる**（`2.0.0` → `2.0.1`）。配布物は main なので「取り下げ」は存在しない

### 誰が何をやるか

| 手順 | 実行者 | 理由 |
|---|---|---|
| 1〜4 | 開発（AI 可） | ローカル/CI で完結する |
| **5** | **人間（ユーザー）** | AI は Cowork セッションを操作できない。cloud 実機での hook 実配線確認は代替手段がない |
| 6 | 開発（AI 可） | 5 の報告を受けて修正 |

**5 を飛ばして「配布完了」と報告しない。** Tier 1 緑は「壊れていないこと」の証明であって、「Cowork で動くこと」の証明ではない。
