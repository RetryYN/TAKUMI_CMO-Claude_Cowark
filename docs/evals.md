# 評価ハーネス（golden タスク集）— 回帰テストの正本

スキル・サブエージェントの「腕が落ちていないか」を確認する固定タスク集。**委譲プロンプトの書き方**: サブエージェントに渡す SKILL.md 参照は絶対パスで明記し「Glob 探索は不要、その Read を直接実行」と指示する（2026-07-23 検証で deliverable-writer が実在する ad-compliance-jp/SKILL.md を「見つからない」と誤報告して停止する flake が発生。再ランでパス直指定により成功）。**LLM 実行が必要なため CI では回せない** — /検証 full の V27 で Cowork 実機（または Claude Code）から回す。PASS 基準は一意に書く（満たす/満たさないが割れない基準）。最終判定は基準に沿って LLM/人間が行う — 「機械的」とは判定者の裁量を残さないという意味で、grep 等の完全自動判定ではない。

## 運用

- 実行結果は `knowledge/verification/<date>-evals.md` に **G1〜G42** の PASS/FAIL 表で記録
- FAIL したらスキル/エージェント本体を直し、直した内容を TESTING.md に記録（golden タスク自体を緩めて直すのは禁止）
- 新しい失敗事例（人間の差し戻し・実運用の見逃し）が出たら golden タスクに追加する（評価駆動: タスク集は育てる）
- **PASS 基準は「その対象の権限で達成できること」だけで書く。** エージェントに、持っていないツールを前提とした基準を課すと**永久に PASS しない golden タスク**になる（2026-07-25: G34 が`deliverable-writer` にアーティファクト発行を要求していた。同エージェントの tools は Read/Write/Edit/Glob/Grep で発行手段が無い）。エージェント向けの基準は**その定義ファイルの出力形式と役割の境界に合わせる**（同日: G20 が `risk-forecaster` に「争点」という合議側の語彙で回答を求めていた。同エージェントの出力形式は FORECAST / 兆候 / 最も安い保険）
- 上記は `tests/test_evals_criteria.py` が機械で突合する（基準が要求する語が対象の本文に無ければ CI が落ちる）
- **網羅は `scripts/lint.py` が保証する**: `skills/*/SKILL.md` と `agents/*.md` のすべてが、少なくとも1つの golden タスクの対象になっていなければ CI が落ちる。スキル・エージェントを新設したら golden タスクも1つ書く（**これが無かったため 2026-07-25 時点で 20本中16本・9体中6体が未収載だった**）
- 全部を毎回回す必要はない。**変更したスキル/エージェントに対応する行だけ**を回すのが平時の運用で、`/検証 perfect`（V27）が全件ラン
