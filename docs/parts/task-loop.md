# 部品: タスク単位のエージェントループ（横断 — 1つの仕事の回し方）

**匠の∞ループはブランドの粒度。この部品はタスク1件の粒度。**

同じ形のループが、これまで成果物の種類ごとにばらばらに書かれていた —
design-artisan→design-critic の2周、pre-send-verifier→承認→outcome-verifier、
設定前の並列合議。**同じ形なのに毎回別々に書かれていると、どれかが抜ける。**
ここが横断の正本で、各部品はこれを具体化したもの。

## 4フェーズ（`docs/agent-tiers.md` の級と1対1）

| フェーズ | 級 | 問い | 主な担い手 |
|---|---|---|---|
| **① 構える** | 戦略級 | **何ができたら終わりか** | `cmo-strategist` / `strategy-advisor` / `growth-challenger` / `risk-forecaster` |
| **② 作る** | 職人級 | 実際に作る | `design-artisan` / `deliverable-writer` |
| **③ 咎める** | 戦術級 | 通すか、止めるか | `design-critic` / `pre-send-verifier` / `privacy-auditor` |
| **④ 確かめる** | 作業者級 | 証跡で確定数を数える | `outcome-verifier` |

③で差し戻し（REVISE / NO-GO / RETHINK / FAIL）なら②へ戻る。**最大2周。**

## 5つの規律（`takumi/domain/task_loop.py` が機械で強制する）

### 1. 何ができたら終わりかを、始める前に書く

**書けないなら、それはまだタスクではなく願望。** 回すほどに「もう少し良くなるかも」で止まらなくなる。

```python
from takumi.domain.task_loop import TaskLoop, LoopPhase, AgentTier
loop = TaskLoop(task_name="LP改善",
                completion_condition="critic が PASS を出し、実測の直帰率が前週を下回る")
# 完了条件が空だと ValueError
```

**完了条件は「作った」ではなく「どうなったら」で書く。**
「モックを3案作る」は作業量であって完了条件ではない。

### 2. 級を飛ばさない・級を取り違えない

```python
loop.record(LoopPhase.MAKE, AgentTier.STRATEGIC, agent="cmo-strategist")
# ValueError: 「作る」は職人級の仕事だが、戦略級のエージェントに委譲しようとしている
```

**上の級に下の作業をさせるのも同じく間違い。** 壁打ち役に成果物を書かせると、
「自分が書いたものを自分で審査する」構図になって咎める側がいなくなる。

### 3. 同じフェーズを続けて回さない

**作る→作る は自己満足**（審査を挟まない反復は品質を上げない）。
**咎める→咎める は基準が無い証拠**（1回で言えないなら基準が言語化できていない）。

### 4. 2周で通らなければ人間に返す

```python
# 2周して REVISE のまま3周目の「作る」に入ろうとすると ValueError
```

**ここまで通らないのは作り方ではなく設計の問題**（完了条件・前提・依頼内容）なので、
回しても収束しない。**残った指摘を「人間レビュー事項」として添えて返す。**

### 5. 確かめずに完了しない

```python
loop.assert_completable()
```

止まる条件は3つ:

- **「確かめる」を通っていない** — 作ったことと効いたことは別
- **最後の審査が差し戻しのまま** — 差し戻しを抱えて引き渡さない
- **不可逆送出なのに `pre-send-verifier` を通っていない** — 送ったものは取り消せない

## ループを短くしてよい場合（省略には理由を宣言する）

| 状況 | 省略できるもの |
|---|---|
| 読み取り・調査だけ（変更操作なし） | ③④（ただし**引用の出所は確かめる**） |
| 下書きの提示まで（公開しない） | ④ |
| 定型の再実行（前回と同じ手順・同じ基準） | ① |

```python
loop = TaskLoop(task_name="週次レポート", completion_condition="…",
                skip_frame_reason="定型の再実行・前回と同じ基準")
```

**理由を書かずに飛ばすと `warnings()` に残る**（止めはしないが、報告に出る）。
**黙って飛ばさせないのがここの役目。**

## 並列との関係

**同時起動は最大4体**（→ `docs/agent-tiers.md`）。このループで並列になるのは:

- **① 構える** の合議（`docs/parts/pre-setup-council.md` — 常設2体、個人データが射程なら3体）
- **① 構える** の壁打ち（`/匠戦略` の守り＋攻めの2体）

**②③④は直列。** 作る側を並列にしても、審査が1本なら詰まるだけ。

## 記録（∞の上りへ）

1. タスクログ（`knowledge/logs/<タスク名>_<日付>.md`）に**周回数と各フェーズの担い手**を書く
2. **2周使ったタスクは理由を1行残す** — 繰り返すなら完了条件の書き方に問題がある
3. 「確かめる」の結果を KPIツリーのノードへ返す（`/匠計測`・`outcome-verifier`）

## コマンドとの接続

**コマンドが入口、このループが中身。**
どのコマンドがどのフェーズを誰に回すかは
**[command-registry.md](../command-registry.md) の「コマンド × タスクループ」表が正本**。

その表を作ったときに分かったこと（2026-07-26）:

> コマンド→手順書→部品→エージェントの到達を機械で数えたら、
> **`/匠顧客`・`/匠設定 ▸ takumi-config`・`takumi-task` の3本がエージェントに一度も届いていなかった。**
> 手順書の文章を読んでいるだけでは気づけない種類の穴だった。

そして**空欄の意味が3通りある**ことも分かった。埋めるときは区別する:

| 空欄の正体 | 例 | どうするか |
|---|---|---|
| **抜け** | `/匠設定` の①（毎朝走る設定を誰も咎めていなかった） | **埋める** |
| **人間が担う** | `/匠顧客` の③（投稿は人間・例外は即エスカレーション） | **「人間」と書く**（省略ではない） |
| **機械が担う** | `/匠設定` の③（Brand Isolation Guard とドメイン層が拒否する） | **仕組みの名前を書く** |

**人やエージェントの目より、拒否できる仕組みのほうが確実な場面では、そちらを③に据える。**

## この部品を使わない場面

- **会話・相談だけ**（成果物が無い）
- **ユーザーが手順そのものを指定している**（その手順が正）
- **危機対応**（`/匠危機対応` が別の順序を持つ。止める→把握→判断→対応）
