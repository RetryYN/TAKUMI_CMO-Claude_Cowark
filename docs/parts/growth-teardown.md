# 部品: 伸びているものの分解（growth-teardown）

**タスク型: リサーチ／分析。** 伸びているアカウント・サイトを実際に開いて観測し、
**自社で試せる仮説**に変えるまでを1本の手順にしたもの。

> **作法の正本は `skills/growth-teardown-jp`。着手前に必ず Read する**（相対不達なら Glob）。
> ここは実行の段取りとシートの型だけを持つ。判断基準は正本側にある。
>
> **前段**: アクティブブランドを確定する（未確定なら /匠設定）。記録は
> `knowledge/brands/<slug>/knowledge/teardowns/` にスコープされる（Brand Isolation Guard 対象）。

## 使う場面

- 「伸びてる◯◯を参考にしたい」「あのアカウントはなぜ伸びてるの？」
- 自社メディア・SNS の**型を決める前**の下調べ
- 競合のメディアを分析したいとき（→ /匠調査 から呼ばれる）

## 段取り

### 1. 対象を選ぶ（3〜5件。ここで結果の8割が決まる）

**有名だからで選ばない。** 選定基準は正本 §1。**必ず「伸びていない同業」を1件入れる**
（差分が取れず、生存者バイアスに落ちるため）。

選んだ理由を1行ずつ書き残す。**後から「なぜこれを見たのか」を再現できるようにする。**

### 2. 一覧で当たりをつける（ここは下準備・結論を出さない）

**実物を開く。まとめ記事で代替しない。** ブラウザ操作が要る場合は `takumi-start` のゲート下。
bot 検知・CAPTCHA・レート制限に遭遇したら**即中断して報告**（/匠調査 の共通ルール）。

| # | 観測項目 | 記録の仕方 |
|---|---|---|
| 1 | 記事・投稿タイトル10本 | **原文のまま。要約しない**（要約すると型が消える） |
| 2 | 連載・カテゴリ・タグの名前 | 一覧をそのまま。**接頭辞【】の有無**も見る |
| 3 | 直近5本の公開日 | 日付のまま（→ 更新頻度を出す） |
| 4 | コンセプト文 | **そのまま引用**（何のメディアだと名乗っているか） |
| 5 | 商品以外の接点 | アプリ・動画・音声・メール・SNS の一覧 |
| 6 | 運営者自身が出している数字 | プレスリリース・IR・決算資料**のみ**。無ければ「記載なし」 |

**6で二次情報の数字を使わない。** まとめ記事の「月間◯万PV」は、
運営者発表に当たれないなら**書かない**（→ `docs/開発ワークフロー.md` §0b の一次情報規律と同じ）。

> **ここで結論を書かない。** 一覧から分かるのは**どの記事を開くか**までである。
> 一覧だけで「本文で売っていない」等と判定するのは推測であり、**実際に外した前歴がある**
> （→ `skills/growth-teardown-jp` §3③）。

### 3. 記事を1本、通しで読む（ここが本体）

対象ごとに代表記事を1本選び、**最後まで読んで**記録する:

| # | 見るもの | なぜ |
|---|---|---|
| 1 | **リード文（冒頭2〜4文）を原文のまま** | **読み手が誰かが最も濃く出る** |
| 2 | **見出し(h2/h3)を順番どおり全部** | **差がつくのは後半の章**（前半は誰でも書ける） |
| 3 | **執筆者・監修者の表記とその位置** | 資格か／当事者性か／使用者としてか＝**何で信じてもらう設計か** |
| 4 | **公開日と更新日** | 制度・法改正ものは**更新日の有無が寿命** |
| 5 | **本文中の自社誘導が何回・どこに・何へ** | 製品／資料／イベント／**ゼロ** |
| 6 | **記事末尾に置かれているもの** | **記事の役割がここに出る** |
| 7 | **内部リンクの送り先** | 読者をどこへ運ぶ設計か |

### 3b. 検索での立ち位置を確かめる（検索狙いの媒体のみ）

記事が狙っているクエリを推定して**実際に検索し、誰が並んでいるかを見る**。

- **並んでいる競合の業種**を書き出す
- **競合のリード文と読み手**を自社候補と比べる
- 問い: 「**このクエリで上位が向いている読み手は誰か。向かれていない読み手はいないか**」

**検索結果の並びを「順位」として報告しない**（ロケール・パーソナライズで変わる）。
**傍証**として扱い、自社記事の実順位は `skills/search-console-jp`（GSC）で実測する。

### 3c. 横断で並べる（1件ずつでは型が出ない）

対象×観測項目の**表**にして**列で読む**。見るのは差分:

- **記事の役割は何か**（見つかる／覚えてもらう／買ってもらう）。
  **役割が違えば「本文で売るか」の正解が逆になる**
- **何で信じてもらっているか**（資格／当事者性／使用者の顔）
- **更新頻度の幅**（自社の工数で入る範囲か）
- **後半の章に何を置いているか**（独自性が出る場所）

### 4. 仮説に変える（ここまでやって完了）

**観測をそのまま真似しない。** 各案を次の形で書く:

```
観測: 〈記事のどこで・何が見えたか。**引用は原文のまま**〉
競合との差分: 〈同じ面に並ぶ他社と、読み手・章立て・書き手のどこが違うか〉
推論: 〈なぜ効いていると考えるか。**推論だと明記する**〉
非対称か: 〈これを競合が真似すると、何を失うか。**失うものが無いなら弱い**〉
資源: 〈自社の工数で再現できるか〉
仮説: 〈誰が・どんな状況で・だからこうすれば・こう変わるはず〉
外れたと分かる条件: 〈これが起きたら間違いだったと分かる〉
```

**「非対称か」を空欄で通さない。** 誰でも真似できることを真似しても、物量のある側が勝つ
（→ `skills/winning-position-jp`）。

- **工数の裏取りは `docs/parts/capacity-plan.md`**（更新頻度と連載は、続けられなければ逆効果）
- **仮説の型は `skills/hypothesis-design-jp`**。反証条件の無い案は出さない
- **優先順は「大きさ ÷ 検証コスト」**

### 5. 記録して接続する（メモで終わらせない）

1. `knowledge/brands/<slug>/knowledge/teardowns/<date>-<対象群>.md` に保存。
   **観測**と**推論**を**別の節**に分ける（混ぜると後から検証できない）
2. **観測日を必ず書く**（サイトは改装される。日付の無い観測は使えない）
3. 採用した仮説は `knowledge/brands/<slug>/hypotheses/backlog.md` へ
4. コンテンツの型に落とすなら **/匠発信**（`takumi-content` で制作、`takumi-ownedmedia` で公開）（`skills/breakout-content-jp` と接続）
5. 媒体運用の型なら **/匠発信**、メディア全体の設計なら **/匠戦略**

## 禁止

- **文章・構成・デザインの複製**（著作権侵害。型を学ぶことと複製は別）
- **競合記事の書き換えによる自社記事の作成**
- **出典の無い数字の引用**（運営者発表に当たれないものは書かない）
- **非公開情報の推測を事実のように書く**（売上・人数・費用）
- **観測と推論を混ぜて書く**
- **ログインが必要な領域への侵入・規約に反する自動収集**（読み取りは公開範囲のみ）
