# 部品: 設定前の合議（pre-setup council）

**後から直すのが高くつく設定を変える前に、必ず立ち止まって複数の観点へ同時に投げる。**
計測基盤（GTM/GA4/GSC）の変更、ワークフローの変更、定常タスクの新規設計など「一度入れると長く効く」判断が対象。

これは助言をもらう工程ではなく**関所**である。合議を通さずに実装へ進まない。

## なぜ立ち止まるのか

実装する側（メインループ）は**手元の具体物から積み上げて考える** — このタグの設定値、この正規表現、この1行。
その視点からは「個々の部品は全部正しいのに、組み合わせると壊れる」種類の問題が見えない。
**視点が違う相手を、同時に、独立に当てる**ことでしか埋まらない穴がある。

順番に相談すると、先の助言が後の助言を汚染する。**並列に投げて、統合はメインループが行う。**

## 手順

### 1. 材料を揃える（合議の前）

投げる前に、判断に必要な現物を集める。**現物なしの合議は一般論しか返ってこない。**

- 現状のエクスポート（GTM ならコンテナ JSON、GA4 なら設定のスクリーンショット・現行チャネル定義）
- 変更案（何を、どう変えるか。曖昧なら先に自分で書き切る）
- 紐づく **KPIツリーのノード**（何のための計測かが決まっていないなら、合議より先に `/戦略`）
- 関連する過去の失敗（`knowledge/feedback/lessons.md`）

**棚卸しはメインループの仕事。** JSON を持っているのはメインループなので、タグ・トリガー・変数の一覧化、
重複の検出、カスタムHTMLタグの有無、PII 混入の疑い箇所の抽出は、委譲せず自分でやる。

### 2. 3体を同時に起動する（並列・独立）

**1回のターンで3つ同時に委譲する。**逐次にしない。

| 相手 | 見るもの | 返るもの |
|---|---|---|
| **risk-forecaster**（fable / 上限時は opus 明示で再委譲） | 構成全体を俯瞰し、**この構成だとどこがどう壊れるか**を先読み。部品ではなく部品間の関係と時間経過 | `FORECAST` + 予測障害（確度・きっかけ・兆候・構造上の原因・打ち手） |
| **privacy-auditor**（opus） | PII 混入・同意・第三者提供・データ規約。**止めるのは取り消せないものに限る**（日本法は EU より緩い — 法が求めていない同意を要求しない） | `VERDICT: GO / GO-WITH-FIXES / NO-GO` |
| **strategy-advisor**（opus） | 運用継続性・ロールバック手段・この判断が長期に効くか | `VERDICT: GO / GO-WITH-CHANGES / RETHINK` |

**各エージェントに正本の本文を同梱する。** 委譲先が接続フォルダ制限で `references/` に到達できない環境がある（escalations E6）。
「読めなければ申告して止まる」は各エージェント側に組み込んであるが、**申告が返ったら本文を同梱して再委譲する**のは呼び出し側の責務。
規範を読めていない監査を、読めた監査のように扱わない。

### 3. 統合して、ユーザーに1枚で見せる

3つの返答をそのまま貼らない。メインループが統合して、判断できる形にする。

- **争点**: 3者の見解が割れた点。割れているという事実が最も重要な情報
- **NO-GO / RETHINK があれば、そこで止める。** 押し切らない
- **兆候の一覧**: risk-forecaster が出した「壊れる前に観測できるサイン」を、監視すべき項目としてまとめる
- **最も安い保険**: 全部は防げない。1つだけ打つならどれか
- **合議の結果を記録**: `knowledge/verification/verdict-log.md` に1行（何を諮り、各VERDICTは何で、人間の最終判断はどうだったか）

### 4. 承認を得てから実装へ

ユーザーの承認なしに設定変更へ進まない。承認後は各スキルの手順（`references/gtm-jp` の「公開の関所」等）に従う。

## いつ呼ぶか / 呼ばないか

**呼ぶ:**

- GTM のタグ・トリガー・変数の追加/変更（公開の有無を問わず、設計の時点で）
- GA4 のチャネルグループ・キーイベント・カスタムディメンションの新設
- 計測する指標そのものの新設（KPIツリーへのノード追加を伴うもの）
- ワークフロー・定常タスクの新規設計、ポリシーやテンプレートの変更

**呼ばない:**

- 読み取りだけの調査・レポート作成
- 決まった手順の繰り返し（定常投稿・巡回・更新）
- すでに合議を通した設計の、同一方針での実行

毎回呼ぶと形骸化する。**「後から直すのが高くつくか」が判定基準。**

## 失敗の型（この部品が防ぐもの）

| 型 | 例 |
|---|---|
| 部品は正しいのに組み合わせが壊れる | タグ単体は正しいが、トリガーの発火順序が保証されておらず、値が入る前に送信される |
| いま動くが後で壊れる | 外部サービスの仕様変更、データ量の増加、検証用フラグの消し忘れ |
| 気づけない | 壊れても誰も気づかず、3か月後に「データが無い」と分かる |
| 取り消せない | 送ってしまった PII、消えたデータ保持期間、公開してしまったタグ |
