# 部品: 設定前の合議（pre-setup council）

**後から直すのが高くつく設定を変える前に、必ず立ち止まって複数の観点へ同時に投げる。**
計測基盤（GTM/GA4/GSC）の変更、ワークフローの変更、定常タスクの新規設計など「一度入れると長く効く」判断が対象。

これは助言をもらう工程ではなく**関所**である。合議を通さずに実装へ進まない。

## なぜ立ち止まるのか

実装する側（メインループ）は**手元の具体物から積み上げて考える** — このタグの設定値、この正規表現、この1行。
その視点からは「個々の部品は全部正しいのに、組み合わせると壊れる」種類の問題が見えない。
**視点が違う相手を、同時に、独立に当てる**ことでしか埋まらない穴がある。

順番に相談すると、先の助言が後の助言を汚染する。**並列に投げて、統合はメインループが行う。**

> **同時起動は最大4体**（→ `docs/agent-tiers.md`）。この合議は常設2体（+ 個人データが射程なら
> `privacy-auditor` で3体）なので上限に収まる。**体数を増やして視点を足そうとしない** —
> 同じ級の似た視点を並べても穴は埋まらず、上限を圧迫して他の委譲を待たせるだけ。

## 手順

### 1. 材料を揃える（合議の前）

投げる前に、判断に必要な現物を集める。**現物なしの合議は一般論しか返ってこない。**

- 現状のエクスポート（GTM ならコンテナ JSON、GA4 なら設定のスクリーンショット・現行チャネル定義）
- 変更案（何を、どう変えるか。曖昧なら先に自分で書き切る）
- 紐づく **KPIツリーのノード**（何のための計測かが決まっていないなら、合議より先に `/匠戦略`）
- 関連する過去の失敗（`knowledge/feedback/lessons.md`）

**棚卸しはメインループの仕事。** JSON を持っているのはメインループなので、タグ・トリガー・変数の一覧化、
重複の検出、カスタムHTMLタグの有無、PII 混入の疑い箇所の抽出は、委譲せず自分でやる。

### 2. 顔ぶれを選ぶ（固定メンバーではない）

**1回のターンで同時に委譲する。**逐次にしない。ただし**誰を呼ぶかは案件で決める。**

**常設（2体）** — 「後から直すのが高くつく」判断には常にこの2つの観点が要る:

| 相手 | 見るもの | 返るもの |
|---|---|---|
| **risk-forecaster**（fable / 上限時は opus 明示で再委譲） | 構成全体を俯瞰し、**この構成だとどこがどう壊れるか**を先読み。部品ではなく部品間の関係と時間経過 | `FORECAST` + 予測障害（確度・きっかけ・兆候・構造上の原因・打ち手） |
| **strategy-advisor**（opus） | 運用継続性・ロールバック手段・この判断が長期に効くか | `VERDICT: GO / GO-WITH-CHANGES / RETHINK` |

**条件付き — privacy-auditor（opus）**: **個人データが実際に案件の射程に入るときだけ呼ぶ。**

呼ぶ / 呼ばないの線引きは明確である:

| 呼ぶ（個人データが射程に入る） | 呼ばない（入らない） |
|---|---|
| フォームの設計・入力値の送信先 | **GTM のタグ・トリガー・変数の設定**（UTM・ページパス・イベント名・クリックIDしか流れない） |
| User-ID の設計、ログインユーザーの識別 | GA4 のチャネルグループ・キーイベント・カスタムディメンションの新設 |
| メール配信・リスト作成・宛先の抽出 | GSC のレポート取得・分析 |
| `knowledge/` に個人が特定できる情報を保存する設計 | KPIツリーへのノード追加、ワークフロー設計 |
| 外部サービスへ顧客データを渡す構成 | |

**なぜ計測タグで呼ばないのか。** GTM が扱うのは UTM パラメータ・ページパス・イベント名・クリックIDであり、
そこに個人情報は含まれない。混入の経路は **URL のクエリ文字列だけ**（サンクスページの `?email=` 等）で、
これはサイト側の作りの問題であり、**`gtm-jp` のプレビュー段階の目視確認とデータ除去機能で塞ぐ定型手順**である。
合議で議論する種類の判断ではない。加えて**カスタムHTMLタグ／カスタムJS変数は `gtm.blocklist` で構造的に禁止**してあるため、
フォームの値を読み取る経路そのものが存在しない。

**個人データが無い案件に監査官を呼ぶと、監査官は無理に指摘を作る。** 実際、AI流入計測の合議では
「CMP が無い」「同意ゲートが無い」を不備として NO-GO が出たが、**それは日本法が要求していないもの**だった（→ `agents/privacy-auditor.md` §2）。
**呼ぶ相手を間違えた合議は、正しい手続きで間違った結論を出す。**

**各エージェントに正本の本文を同梱する。** 委譲先が接続フォルダ制限で `skills/` に到達できない環境がある（escalations E6）。
「読めなければ申告して止まる」は各エージェント側に組み込んであるが、**申告が返ったら本文を同梱して再委譲する**のは呼び出し側の責務。
規範を読めていない監査を、読めた監査のように扱わない。

### 3. 統合して、ユーザーに1枚で見せる

返答をそのまま貼らない。メインループが統合して、判断できる形にする。
**誰を呼び、誰を呼ばなかったか（とその理由）も1行で書く。**

- **争点**: 見解が割れた点。割れているという事実が最も重要な情報
- **NO-GO / RETHINK があれば、そこで止める。** 押し切らない
- **兆候の一覧**: risk-forecaster が出した「壊れる前に観測できるサイン」を、監視すべき項目としてまとめる
- **最も安い保険**: 全部は防げない。1つだけ打つならどれか
- **合議の結果を記録**: `knowledge/verification/verdict-log.md` に1行（何を諮り、各VERDICTは何で、人間の最終判断はどうだったか）

### 4. 承認を得てから実装へ

ユーザーの承認なしに実装へ進まない。承認後は各スキルの手順（`skills/gtm-jp` / `ga4-jp`）に従う。

## いつ呼ぶか / 呼ばないか

判定基準は**「後から直すのが高くつくか」**の一点。**手順が重いかどうかではない。**

**呼ぶ:**

- **計測する指標そのものの新設**（KPIツリーへのノード追加を伴うもの）— 何を成果とみなすかの定義であり、後から変えると過去との比較ができなくなる
- **GA4 のカスタムディメンション/指標の設計** — 上限があり、削除しても48時間は作り直せず、カーディナリティを誤るとデータが `(other)` に落ちる
- **GA4 のチャネルグループの定義** — 過去データに遡って再処理され、レポートの見え方が全部変わる
- ワークフロー・定常タスクの新規設計、ポリシーやテンプレートの変更

**呼ばない:**

- **GTM のタグ・トリガー・変数の設定**（公開を含む）— **バージョンの「最新バージョンに設定」で戻せる**。
  プレビューで確認して公開し、壊れたらロールバックする。これは正しく設定するだけの通常作業であって、諮る判断ではない
- GA4 のキーイベントの追加（影響が閉じている。解除だけは承認を取る）
- 読み取りだけの調査・レポート作成
- 決まった手順の繰り返し（定常投稿・巡回・更新）
- すでに合議を通した設計の、同一方針での実行

**毎回呼ぶと形骸化する。** 戻せる作業に関所を置くと、関所そのものが軽く扱われるようになり、
本当に戻せない判断のときに機能しなくなる。

## 失敗の型（この部品が防ぐもの）

| 型 | 例 |
|---|---|
| 部品は正しいのに組み合わせが壊れる | タグ単体は正しいが、トリガーの発火順序が保証されておらず、値が入る前に送信される |
| いま動くが後で壊れる | 外部サービスの仕様変更、データ量の増加、検証用フラグの消し忘れ |
| 気づけない | 壊れても誰も気づかず、3か月後に「データが無い」と分かる |
| 取り消せない | 送ってしまった PII、消えたデータ保持期間、公開してしまったタグ |
