# 定量調査の設計と読み方

**数字は、それらしく見えるほど危ない。**

「n=30 で 60% が『欲しい』と答えました」は、何も言っていないに等しい。
**誰に聞いたか・何人に聞いたか・どう聞いたかで、数字はいくらでも動く。**

このスキルの目的は、**自社の調査で嘘をつかないこと**と、
**他社の調査を鵜呑みにしないこと**。

> **本プロダクトの原則との関係**: 「**判定不能を『効果あり』と書かない**」
> （→ `skills/hypothesis-design-jp`）の定量版がここ。
> **差が確認できなかったこと**と**差が無いこと**は違う。

## 0. 調査を始める前に

**「調べたい」ではなく「これが分かったら、何を変えるのか」から始める。**
答えが「特に何も」なら、その調査はやらない（→ `skills/hypothesis-design-jp` §2）。

| 決めること | なぜ先に決めるか |
|---|---|
| **何が分かったら、何をするか** | 使わないデータを集めない |
| **判定の基準**（何%以上なら実施する等） | **後から基準を決めると、結果に都合よく合わせてしまう** |
| **誰に聞くか**（母集団） | ここが分析の質の大半を決める |
| **何人に聞くか** | §1 |
| 期間 | 季節性の混入を避ける（→ `skills/demand-timing-jp`） |

**基準を先に固定する。** これを守らないだけで、調査は「やった証拠」に堕ちる。

## 1. 何人に聞けばいいか

### 目安（比率を推定する調査・母集団が十分大きい場合）

| n | 誤差の幅の目安（95%水準・比率50%付近） |
|---|---|
| 100 | 約 ±10 ポイント |
| 400 | 約 ±5 ポイント |
| 1,000 | 約 ±3 ポイント |

**読み方**: n=100 で「60%」と出たら、**実際は 50〜70% のどこか**。
**n=100 の 60% と 55% は、区別できない。**

- **比率が 50% から離れるほど誤差は小さくなる**（極端な結果ほど安定する）
- **母集団が小さいとき（社員300人など）は、必要数はもっと少なくて済む**
- **セグメント別に見るなら、セグメントごとに人数が要る。**
  全体 n=400 でも、5分割すれば各80人＝誤差 ±11 ポイント。
  **「全体では十分」は、内訳では十分ではない**

### 中小規模の現実

**多くの場合、統計的に十分な n は集まらない。** そのときは:

- **定量で結論を出そうとしない。** `/顧客の声`（定性）で**深く聞く**ほうが情報量が多い
- **数字を出すなら必ず「n=◯」を併記する**（n を書かない数字は使わない）
- **「傾向」と書き、「〜%が求めている」と書かない**

**n が足りないことは失敗ではない。足りないのに断定するのが失敗。**

## 2. 誰に聞くか — サンプル数より偏りのほうが致命的

**n を増やしても、偏りは直らない。** ここが最も誤解される。

| 偏り | どこで起きるか | 対処 |
|---|---|---|
| **生存者バイアス** | 既存顧客・継続者だけに聞く | **去った人・買わなかった人に当たる**（→ `/顧客の声`） |
| **回答者バイアス** | 答えてくれる人は熱心な人 | 回収率を記録し、**無回答層の性質を推測して明記** |
| **募集経路バイアス** | 自社SNSで募る＝ファンばかり | 経路を分ける・**経路を必ず明記** |
| **謝礼バイアス** | 謝礼目当ての回答 | 所要時間・スクリーニング設問 |
| **タイミング** | キャンペーン直後・繁忙期 | 期間を明記（→ `skills/demand-timing-jp`） |

**「自社のメルマガ読者1,000人に聞きました」は、n=1,000 の価値を持たない。**
**すでに自社を好きな人1,000人**の意見であり、市場の意見ではない。

**調査結果を書くときは、n と一緒に「誰に・どこで・いつ聞いたか」を必ず書く。**

## 3. どう聞くか — 設問が答えを作る

| やってはいけない設問 | なぜ | 直し方 |
|---|---|---|
| 「この機能があったら使いますか？」 | **未来の行動の自己申告は当たらない** | 「前回それが必要になったのはいつか。そのとき何をしたか」 |
| 「◯◯は重要だと思いますか？」 | ほぼ全員が「はい」 | **複数の項目を順位づけさせる／トレードオフを迫る** |
| 「便利な◯◯についてどう思いますか」 | 誘導（前提を含む） | 形容詞を外す |
| 「価格は安いほうがいいですか？」 | 答えが自明 | §5 の価格調査 |
| 「AとBのどちらが良いですか」（説明が非対称） | 説明の量が答えを作る | 同じ粒度で書く |
| 1問に2つ聞く（「使いやすく安いか」） | どちらへの回答か不明 | 分ける |

**選択肢の設計**:

- **「その他」と「わからない」を必ず置く**（無いと、選択肢の中に押し込まれる）
- **順序効果**がある（先頭が選ばれやすい）。可能なら順序をランダム化する
- **5段階の真ん中に逃げられる**。強制したいなら4段階にする（ただし**逃げ道を塞ぐこと自体が歪み**）

**満足度は「満足しましたか」で聞かない。** 具体的な行動で聞く
（また使うか・人に勧めたか・実際に何をしたか → `skills/referral-advocacy-jp`）。

## 4. 差を読む — 「差が出た」の大半は誤差

### 判定の順序

1. **母数を見る**（各群の n。**両方**）
2. **差の幅と誤差の幅を比べる**（§1。誤差の幅より小さい差は、差と呼ばない）
3. **その差に意味があるか**（統計的な差 ≠ 実務的な意味。**0.3ポイントの改善に価値があるか**）
4. **他の要因を潰したか**（期間・季節・同時に変えた施策 → `skills/demand-timing-jp` §7）

### 言葉の使い分け（ここを厳密に）

| 状況 | 書き方 |
|---|---|
| 差が誤差の幅を超えている | 「差が確認できた（n=◯、期間◯）」 |
| 差が誤差の幅に収まる | **「差は確認できなかった」**（「差が無い」ではない） |
| 母数不足 | **「判定不能」**（→ `takumi/domain/unit_economics.py` と同じ扱い） |
| 要因を切り分けていない | **「要因未特定」**（→ `skills/logical-writing`） |

**「差が確認できなかった」を「同じだった」と書かない。**
**「有意差なし」は「効果なし」の証明ではない。**

### やってはいけないこと

- **有意になるまで検定を繰り返す**（見るたびに「当たり」が出る）
- **後から都合の良いセグメントを探す**（分割を増やせば必ずどこかで差が出る）
- **目標に達したところで止める**（→ 判定基準と期間を**着手前に固定**する §0）
- **相関を因果と書く**（→ `skills/logical-writing`）

**オーガニック運用では、そもそも A/B テストの母数が足りないことが多い。**
そのときは**逐次改善と前後比較・コホートの縦読み**にする
（→ `skills/cro-jp`・`skills/customer-analytics-jp` §2）。

## 5. 価格を調べる — 「いくらなら買いますか」は聞かない

**直接聞くと、安く答える。** 支払う場面ではないから。

| 手法 | 何が分かるか | 注意 |
|---|---|---|
| **PSM（価格感度分析）** | 「高すぎる／安すぎる／高いと感じ始める／安いと感じ始める」の4問から受容価格帯 | **回答者が価値を理解していないと無意味**。商品説明を先に十分読ませる |
| **コンジョイント分析** | 組合せを選ばせ、**どの要素にいくら払うか**を推定 | 設計が難しく n も要る。**中小規模では過剰なことが多い** |
| **MaxDiff** | 項目群から「最も重要／最も不要」を選ばせ、優先順位を出す | 順位づけより回答負荷が低い |
| **実際に売ってみる** | **最も確実** | 小さく試す（→ `skills/hypothesis-design-jp` §4） |

**中小規模での現実的な優先順は「実際に売ってみる > PSM > その他」。**
調査に時間をかけるより、**小さく売って確かめるほうが速く、確からしい**。

**価格の設計そのものは `skills/offer-design-jp`。**
値付けは最後に触る（§6 の順番）。

## 6. 他社の調査データを引用するとき

**数字を見たら、必ずこの4つを確認する。確認できないなら引用しない。**

1. **誰が調査したか**（利害関係があるか。**その商品を売る会社の調査は、その商品に有利に出る**）
2. **誰に聞いたか**（母集団と募集経路）
3. **何人か**（n。書いていない調査は使わない）
4. **いつか**（古い調査を現在形で書かない）

**まとめ記事やニュース記事の数字を、原典に当たらず引用しない**
（→ `docs/開発ワークフロー.md` §0b、`skills/growth-teardown-jp` §0）。

**公的統計は最も安全な引用先**（→ 出典欄）。ただし**定義を確認する**
（「世帯」「事業所」「就業者」の定義は調査によって違う）。

## 7. 報告の型

```
問い: 〈何を決めるための調査か〉
方法: 〈誰に・どこで・いつ・何人に・どう聞いたか〉
結果: 〈数字。**n と期間を必ず併記**〉
判定: 〈差が確認できた／確認できなかった／判定不能／要因未特定〉
限界: 〈偏り・確かめられなかったこと〉
だから何をするか: 〈誰が・いつ・何を〉
```

**「限界」を空欄にしない。** 偏りの無い調査は存在しない。
**書かれていない限界は、読み手が気づかないまま意思決定に混ざる。**

## 8. よくある失敗

- **判定基準を後から決める**（結果に都合よく合わせてしまう）
- **n を書かない**（書かない数字は使わない・使わせない）
- **n を増やせば偏りが直ると思う**（**偏りは n では直らない**）
- **自社のファンに聞いて市場の意見として書く**
- **「あったら使いますか」と聞く**（未来の自己申告は当たらない）
- **誤差の幅より小さい差を「改善した」と書く**
- **「差が確認できなかった」を「同じ」「効果なし」と書く**
- **有意になるまで検定を繰り返す／都合の良いセグメントを後から探す**
- **「いくらなら買いますか」と直接聞く**（安く答える）
- **他社調査を原典に当たらず引用する**（調査主体の利害を確認していない）
- **限界を書かない**（読み手が気づかないまま意思決定に混ざる）
