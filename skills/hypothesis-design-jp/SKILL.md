# 仮説設計

**マーケティングのプロは、仮説づくりのプロである。**

データは「**何が起きたか**」しか語らない。「**なぜ**」は必ず推論になる。
その推論の質が施策の質を決め、施策の質が結果を決める。**ここが本体で、実行は写像にすぎない。**

> **ゼロ広告費との関係**: 広告費があれば「たくさん試して当たりを拾う」ができる。**それが使えない以上、
> 1回の打席の質を上げるしかない。** 仮説の精度が、そのまま資源効率になる。

## 0. 「とりあえずやってみる」を殺す

施策を提案する前に、**この文が埋まるか**を確かめる。埋まらないなら、それは施策ではなく思いつき。

```
〈誰〉が〈どんな状況〉で〈どうしている〉。
それは〈なぜなら〉だと考えられる。
だから〈こうすれば〉〈これがこう変わる〉はずだ。
外れたと分かるのは〈これが起きたとき〉。
```

最後の1行が最も重要。**何が起きたら間違いだったと分かるかを言えない仮説は、仮説ではない。**
それは願望であり、どう転んでも「学び」が出ないので、次に進めない。

## 1. 仮説の作り方 — 観察 → 違和感 → 問い → 仮説

**いきなり仮説から始めない。** 順序を守ると質が上がる。

| 段階 | やること | 失敗例 |
|---|---|---|
| **観察** | 事実を集める。解釈をまだ入れない | 「流入が減った」ではなく「◯月から検索流入が3割減、SNSは横ばい」 |
| **違和感** | 予想と違う点を1つ特定する | 「全体的に良くない」← 違和感ではない。特定できていない |
| **問い** | 違和感を疑問文にする | 「なぜ検索だけが減ったのか」 |
| **仮説** | 問いへの、検証できる答え | 上の §0 の型で書く |

**違和感が特定できないなら、観察が足りない。** 仮説をひねり出そうとせず、観察に戻る。

### 違和感を見つける4つの視点

| 視点 | 問い |
|---|---|
| **差分** | 前と比べて何が変わったか。他と比べて何が違うか |
| **例外** | うまくいっている一部は何が違うのか（**成功例の中に仮説がある**） |
| **矛盾** | 数字と現場の実感が食い違っているのはどこか |
| **不在** | あるはずのものが無いのはどこか（競合が誰も言っていない・顧客が触れない） |

**「例外」が最も打ち手に近い。** 12本中2本だけ伸びた記事があるなら、その2本の共通点が仮説の原料。

## 2. 良い仮説の条件

| 条件 | 説明 | 満たさない例 |
|---|---|---|
| **反証可能** | 外れたと分かる条件が言える | 「認知が足りない」← 何が起きたら足りていたと言えるのか |
| **具体的** | 誰の・どの行動が変わるか言える | 「もっと魅力を伝える」 |
| **意外性がある** | すでに知っていることの確認で終わらない | 「良い記事を書けば読まれる」 |
| **打ち手に近い** | 明日できる行動に落ちる | 「ブランド力を上げる」 |
| **1つに絞れている** | 検証で切り分けられる | 「デザインと文章と価格を直せば」 |

### 意外性の測り方

**「これが正しかったら、自分たちは何を変えることになるか」** に答える。
答えが「特に何も」なら、その仮説は検証する価値がない（当たっても外れても行動が変わらない）。

## 3. 仮説の強さを見積もる（賭ける前に）

| 軸 | 見るもの |
|---|---|
| **根拠の質** | 一次情報か（VOC・実測）／二次情報か／推測か。**推測なら推測と書く** |
| **検証コスト** | 確かめるのに何時間かかるか（→ `docs/parts/capacity-plan.md`） |
| **当たったときの大きさ** | どのKPIノードが、どのくらい動くか |
| **外れたときの損失** | 取り返せるか。取り返せないなら賭けない |

**優先順は「大きさ ÷ 検証コスト」。** 確からしさが最優先ではない。
**確実なものばかり選ぶと、確実に小さい結果しか出ない。**

## 4. 検証の設計 — 小さく、速く、切り分けられる形に

1. **何を測れば決着がつくか**を先に決める（→ `skills/kpi-design-jp`）。指標も期間も**着手前に固定**する
2. **1回で1つだけ変える**（複数変えると、当たっても理由が分からない＝次に活かせない）
3. **最小の形で試す**（記事1本・投稿3本・1セグメント。全面展開しない）
4. **母数が足りないときは A/B にしない** — 逐次改善と前後比較にする（→ `skills/cro-jp`）。
   オーガニック運用では**これが平常運転**
5. **打ち切り条件を決めておく**（いつまでに何が起きなければ止めるか）

**「やってみて様子を見る」を計画に書かない。** それは検証ではなく先送り。

## 5. 外れたときにこそ学ぶ

**外れた仮説は失敗ではない。学びが出なかったときだけが失敗。**

外れたら、次の3つのどれかを特定する:

| 何が違ったか | 次にすること |
|---|---|
| **前提が違った**（顧客の状況の読み違い） | `/匠顧客` に戻る。**推測で埋めた前提が覆った＝最大の収穫** |
| **因果が違った**（Aを変えてもBは動かない） | ツリーの親子関係を疑う（→ `skills/kpi-design-jp`） |
| **実行が違った**（仮説は合っていたが届いていない） | 量・タイミング・見せ方を疑う。仮説は捨てない |

**この3つを切り分けずに「効果がなかった」で終わらせない。** 切り分けないと、
正しい仮説を捨てたり、間違った仮説を粘ったりする。

### 学びの記録

`knowledge/brands/<slug>/hypotheses/<date>-<件名>.md` に:

- 仮説（§0 の型のまま）
- 検証方法・期間・母数
- 結果（**数字。母数つき**）
- **判定**（支持／不支持／判定不能）
- **どれが違ったか**（前提／因果／実行）
- **次の仮説**

**「判定不能」を正直に書く。** 母数不足・要因が混ざった・測れていなかった、はすべて判定不能。
判定不能を「効果あり」と書くのが最も高くつく（間違った学習が残る）。

## 6. 仮説の在庫を持つ

**思いついたときに実行するのではなく、貯めて選ぶ。**

`knowledge/brands/<slug>/hypotheses/backlog.md` に、§0 の型で書いた仮説を並べる。
各行に「根拠の質・検証コスト・当たったときの大きさ」を付ける。

- **週に1度、上位から選んで着手する**（思いつき順ではなく、大きさ ÷ コスト順）
- **在庫が5本を切ったら、観察に時間を割く**（打ち手が枯れているのではなく、観察が枯れている）
- 検証済みのものは「支持／不支持」を残して**捨てない**（同じ仮説を2年後にまた立てるのを防ぐ）

## 7. よくある失敗

- **観察を飛ばして仮説から始める**（自分が既に信じていることを補強するだけになる）
- **反証条件を書かない**（どう転んでも「手応えはあった」で終わる）
- **一度に複数変える**（当たっても理由が分からず、再現できない）
- **確実な仮説ばかり選ぶ**（確実に小さい結果しか出ない）
- **外れたときに仮説ごと捨てる**（実行が違っただけかもしれない）
- **相関を因果と読む**（「変えた週に増えた」だけなら**要因未特定**と書く → `skills/logical-writing`）
- **判定不能を「効果あり」と書く**（間違った学習が組織に残り、以後の判断を歪める）
