# 需要の山に乗る

**同じ中身でも、出す時期で結果は変わる。しかも時期を選ぶのは無料。**

広告は「今すぐ露出を買う」ことができる。ゼロ広告費ではそれができない代わりに、
**需要が自然に立ち上がる瞬間に、すでにそこに在る**という戦い方ができる。

**これは「間に合わせる」ゲームである。** 山が来てから作り始めた時点で負けている。

> **ゼロ広告費との関係**: 検索・SNS・メールのいずれも、需要が高い時期は**同じ努力で反応が増える**。
> 逆に言えば、**需要の無い時期に力を使うのが最大の無駄**。時期の設計は、資源配分そのもの。

## 0. 3種類の「山」を分けて扱う（混ぜると必ず失敗する）

| 種類 | 例 | 予測できるか | 準備期間 | 判断者 |
|---|---|---|---|---|
| **暦の山** | 年度・祝日・長期休暇・季節行事 | **できる（確実）** | 数か月前から | AI が計画できる |
| **業界の山** | 決算期・展示会・法改正の施行・繁忙期 | **できる（要調査）** | 数か月前から | AI が調べて提案 |
| **時事の山** | ニュース・話題・流行 | **できない** | 数時間〜数日 | **人間が判断する** |

**時事に乗る判断を AI が自律で行わない。** 話題の性質（誰かの不幸・事故・災害・係争）を
読み違えたときの損失が大きすぎる（→ §5）。

**計画の骨格は暦と業界の山で組む。時事は余白として持つ。**
時事頼みの計画は、当たれば大きいが**積み上がらない**（→ `skills/winning-position-jp` §4）。

## 1. 暦の山 — 日本の年間カレンダー

### 国民の祝日（内閣府・国民の祝日に関する法律 第2条）

| 名称 | 期日 | 名称 | 期日 |
|---|---|---|---|
| 元日 | 1月1日 | 海の日 | 7月の第3月曜日 |
| 成人の日 | 1月の第2月曜日 | 山の日 | 8月11日 |
| 建国記念の日 | 2月11日 | 敬老の日 | 9月の第3月曜日 |
| 天皇誕生日 | 2月23日 | 秋分の日 | 秋分日 |
| 春分の日 | 春分日 | スポーツの日 | 10月の第2月曜日 |
| 昭和の日 | 4月29日 | 文化の日 | 11月3日 |
| 憲法記念日 | 5月3日 | 勤労感謝の日 | 11月23日 |
| みどりの日 | 5月4日 | | |
| こどもの日 | 5月5日 | | |

**振替休日**: 「祝日が日曜日に当たるとき、その日後においてその日に最も近い『祝日でない日』を休日とする」。
**国民の休日**: 「その前日及び翌日が『祝日』である日（『祝日でない日に限る』）は、休日とする」。

**春分の日・秋分の日は日付が固定されていない**（前年2月の官報で公告される）。
**カレンダーを固定日で作らない。**

### 日本特有の周期（暦以外）

| 周期 | 何が起きるか | いつ準備するか |
|---|---|---|
| **年度（4月始まり）** | 予算・人事・新生活。BtoB の意思決定が動く | **1〜2月**（年度末の駆け込みと新年度の検討が重なる） |
| **決算期（3月・9月に集中）** | 予算消化・稟議 | 2か月前 |
| **長期休暇（GW・お盆・年末年始）** | BtoB は止まり、BtoC は動く。**業種で真逆** | 1か月前 |
| **賞与（6〜7月・12月）** | 高単価の検討が動く | 1か月前 |
| **年末年始** | 振り返りと計画。「来年」の検索が立つ | **11月**（12月では遅い） |

**BtoB と BtoC で山が逆になる時期がある。** 自社がどちらかを確かめずに
一般論のカレンダーを適用しない。

## 2. 業界の山 — 調べて特定する

**一般的な歳時記より、自社の業界の周期のほうが効く。** 調べる先:

1. **自社の過去データ**（最も確実）— GA4 の年次比較・GSC の1年分（→ `/計測`）
2. **顧客に聞く**（「いつ検討を始めるか」→ `/顧客の声`）
3. **業界の年次イベント**（展示会・学会・業界紙の特集）
4. **制度の施行日**（法改正・補助金の公募・申請期限）
5. **公的統計**（家計調査など。→ §3）

**制度の施行日は最も確実な山。** 施行の**数か月前**から検索が立ち、
**そのとき既に記事があるかどうか**で結果が決まる。

## 3. 検索需要の季節性を読む（データで確かめる）

### Google トレンドの正しい読み方（公式）

- **正規化されている**: 「相対的な人気度を比較するため、各データポイントが、対象の地域と期間における検索の合計数で割られます」
- **0〜100 は相対値**: 「その算出された数値が、すべてのトピックの総検索数に対する特定のトピックの割合に基づいて、0〜100の範囲で調整されます」
- **地域間で絶対量は比較できない**: 「異なる地域で特定の検索キーワードの検索インタレストが同じであっても、必ずしも検索ボリュームの合計が同じであるとは限りません」
- **サンプルである**: 「Google トレンドで使用される Google 検索のサンプルは1つのみですが、Google では1日に何十億件もの検索を処理しているため、これが十分な数です」
- **小さいものは 0 と出る**: 「検索ボリュームの小さいキーワードは『0』と表示されます」

**実務上の読み替え（ここを間違える人が多い）**:

1. **100 は「多い」ではなく「その期間の中で最大」。** 期間を変えれば 100 の位置は動く。
   **異なるスクリーンショットの数値を並べて比較しない**
2. **0 は「需要ゼロ」ではない。** 閾値未満なだけ。ニッチ語では常時 0 になりうる
3. **地域比較は割合の比較**。「東京より地方のほうが関心が高い」は言えても「検索数が多い」は言えない
4. **山の「形」と「時期」を読む道具であって、量を測る道具ではない**

**トレンドで時期を当て、量は GSC の実測で確かめる**（→ `skills/search-console-jp`）。

### 公的統計で裏を取る

**家計調査**（総務省統計局）は、品目別・月別の支出を公表しており、
**消費財の季節性を実データで確かめられる**（`https://www.stat.go.jp/data/kakei/`、
データベースは e-Stat）。

**「◯月に売れるらしい」を、憶測のまま計画に入れない。**
自社データ → 公的統計 → トレンド、の順に確からしい。

## 4. 逆算する — 「間に合わせる」ための設計

**山の当日に出しても遅い。** 検索も推薦も、**評価が乗るまでに時間がかかる**。

| 施策 | いつ公開するか | 理由 |
|---|---|---|
| **検索を狙う記事** | **山の3〜6か月前** | 順位が付くまでに時間が要る。**当日公開は間に合わない** |
| **既存記事の更新** | 山の1〜2か月前 | 新規より速く効く。**まず既存を見る** |
| **SNS 投稿** | 山の直前〜当日 | 即時性が効く面 |
| **メール** | 山の1〜2週間前 | 検討の開始に合わせる |

**新規記事を書く前に、既存記事の更新を検討する。**
同じ山に対して、**すでに評価が乗っている記事を直すほうが速く、安い**。

### 年間カレンダーの作り方

1. **暦の山を置く**（§1。祝日は毎年の官報で確認。固定日にしない）
2. **業界の山を重ねる**（§2）
3. **自社の実測を重ねる**（過去2年の GA4・GSC の月別）
4. **逆算して着手日を書く**（上の表の準備期間を引く）
5. **山と山の間に「積み上げる仕事」を置く**（→ §6）
6. **余白を1〜2割残す**（時事と、外れたときの作り直し）

保存先: `knowledge/brands/<slug>/strategy/demand-calendar.md`。
実行の割り付けは `docs/parts/content-calendar.md`、工数の上限は `docs/parts/capacity-plan.md`。

**カレンダーは容量を超えて作らない。** 山を全部取りにいくと、どの山でも間に合わない。
**取りにいく山を決める＝取りにいかない山を決める**（→ `skills/winning-position-jp` §5）。

## 5. 時事の山 — 乗るかどうかは人間が決める

**乗ってよいか**の判定。**1つでも「いいえ」なら乗らない。**

| 問い | 判定 |
|---|---|
| その話題に、**自社が語る資格**があるか（一次情報・実務経験） | 無いなら、ただの便乗 |
| **誰かの不幸・事故・災害・係争**を材料にしていないか | していたら**乗らない**（例外なし） |
| **柱のどれか**に紐づくか（→ `skills/messaging-design-jp`） | 紐づかないなら、その場限りの消費 |
| **事実確認ができているか** | 速報段階の情報を根拠にしない |
| **半年後に読み返して恥ずかしくないか** | 恥ずかしいなら出さない |

**AI は「乗る/乗らない」の判断を自律で行わない。** 案として提示し、**人間が決める**。
災害・事故の発生時は、**予約投稿を止めることのほうが優先**（→ `/危機対応`）。

**時事に乗ると決めたら速さが全て**だが、**速さのために事実確認を飛ばさない。**
外した便乗は、乗らなかった場合よりはるかに高くつく。

## 6. 山が無い時期に何をするか（ここで差がつく）

**閑散期は暇な時期ではなく、仕込みの時期。**

- **次の山の記事を書く**（§4 の逆算がここに落ちる）
- **既存コンテンツを更新する**（積み上げの複利。→ `skills/seo-jp`）
- **一次情報を取る**（`/顧客の声`・自社データの集計）
- **当たりの分析をする**（→ `skills/breakout-content-jp` §6）
- **仮説の在庫を作る**（→ `skills/hypothesis-design-jp` §6）

**閑散期に発信量を落とすと、山のときに配信面での評価が落ちている。**
**量は落としても、止めない**（YouTube 公式は「アップロード頻度が通常より少ない」ことを
伸び悩みの原因として挙げている → `skills/breakout-content-jp`）。

## 7. 測る — 「季節だったのか、施策だったのか」を切り分ける

**季節性は、最も見落とされる交絡要因。**

- **前年同月と比べる**（前月比だけで語らない）
- **競合を含めた比率で見る**（自社単独の増減は市場全体の季節変動と区別できない
  → `skills/kpi-design-jp` のシェア・オブ・サーチ）
- **「山だから伸びた」を施策の成果に数えない**（→ `outcome-verifier`）
- **外したら、時期の読みか中身かを切り分ける**（→ `skills/hypothesis-design-jp` §5）

**季節要因を排除せずに「施策が効いた」と書かない。** 間違った学習が翌年まで残る。

## 8. よくある失敗

- **山の当日に出す**（検索は間に合わない。3〜6か月前に逆算する）
- **新規記事から作る**（既存記事の更新のほうが速く安い）
- **祝日を固定日でカレンダーに入れる**（春分・秋分は年で動く。振替休日も動く）
- **一般的な歳時記をそのまま適用する**（BtoB と BtoC で山が逆になる時期がある）
- **Google トレンドの 0〜100 を検索数として扱う**（正規化された相対値。期間を変えれば動く）
- **異なる期間・地域のトレンド値を並べて比較する**（比較できない）
- **時事に AI の判断で乗る**（誰かの不幸を材料にする事故が起きる）
- **山を全部取りにいく**（どれも間に合わない。取りにいかない山を決める）
- **閑散期に発信を止める**（山のときに配信面での評価が落ちている）
- **季節要因を排除せずに施策の成果と書く**（前年同月・競合比で確かめる）
