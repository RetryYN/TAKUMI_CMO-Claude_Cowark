# /匠戦略 ▸ 複数媒体の統括（takumi-campaign）

匠の∞ループの**打ち手（統括）**。戦略（上流）が流した「計画」を受け、**複数のオーガニック媒体を1つの目標の下に束ねて**オーケストレーションする。すべて**ゼロ広告費**（有料出稿は組み込まない）。

> **前段**: アクティブブランドを確定する（未確定なら /匠設定）。計画は `knowledge/brands/<slug>/strategy/campaigns/` にスコープされる（Brand Isolation Guard 対象）。

## 手順

1. **目標の確定**: このキャンペーンで動かす **KPIツリーのノード**を1つ選ぶ（`knowledge/brands/<slug>/strategy/kpi-tree.yaml` から。無ければ /匠戦略 を先に）。期間と達成水準（仮でも根拠つき）を決める。
2. **参加媒体の選定**（オーガニックのみ）: **SNS・コンテンツ・Webサイト・オウンドメディア・メール**（いずれも `/匠発信` の配下）**＋ 広報・連携**（`/匠広報`） から、目標に効く媒体を選ぶ（`ChannelKind` の6種と1対1。各媒体の実行は該当パックが担う。**Owned 5種 + Earned 1種で、Paid は構造的に持たない**）。各媒体の役割（認知/流入/転換/信頼）を割り当てる。**媒体を足す前に `docs/parts/capacity-plan.md` の埋まり具合を見る** — 100%を超えるなら足さず、落とす候補を先に決める（消化できない計画は最初から嘘だった計画）。
2b. **モダリティの面を張る（包囲網の形成）**: 媒体だけでなく**テキスト／画像／動画**の3モダリティで露出面を設計する。1本の主張を、記事（`/匠発信 ▸ takumi-ownedmedia`）・投稿（`takumi-sns`）・画像/バナー・動画（`takumi-content`）へ**同じ骨子のまま形を変えて**展開する。テキスト1本は点にすぎず、モダリティを横断して初めて面になる — **これが「AI に届く」の実体**（複数モダリティ・複数露出面から反復して現れるものを AI は認知し推奨する）。キャンペーン YAML に `modalities:` として、どのモダリティを誰がいつ担うかを明記する。**媒体を増やす前に、いま持っている主張のモダリティ展開が埋まっているかを先に見る**（1記事を動画・画像に展開するほうが、新媒体を1つ足すより面が濃くなる）。
2c. **時期を決める（需要の山に合わせる）**: `skills/demand-timing-jp` に従い、目標に対して**いつ出すか**を決める。`knowledge/brands/<slug>/strategy/demand-calendar.md` があれば読む（無ければここで作る）。**山の当日に出しても遅い** — 検索を狙う記事は**3〜6か月前**、既存記事の更新は1〜2か月前、SNS は直前〜当日、メールは1〜2週間前に逆算する。**新規制作の前に、既存コンテンツの更新で同じ山を取れないかを先に見る**（速く、安い）。時事の話題に乗るかどうかは**人間が判断する**（AI は案の提示までで、自律で乗らない）。
2d. **役割の重複を潰す**: 選んだ媒体に **1媒体1役割**（見つかる／知られる／信じられる／思い出される／買われる／語られる）が割り当たっているか確認する（→ `skills/channel-planning-jp`）。**同じ役割の媒体が2つあるなら、片方を落とすか役割を分ける** — 5媒体で同じことをやれば、5媒体ぶんの手間で1媒体ぶんの効果しか出ない。**ゼロ広告費で最も弱くなるのは「知られる」**（広告が担う部分）なので、SNS と `/匠広報`（Earned）で埋まっているかを見る。各媒体の指標は**1〜2個に絞り、KPIツリーのノードに紐づける**。
3. **計画化**: docs/parts/content-calendar.md（計画部品）で、媒体横断のカレンダー・配信計画を作る。**表で終わらせず** queue.md 反映と定常タスク化（/匠設定）まで接続する。
4. **統括ファイルの保存**（アクティブ区画内）: `knowledge/brands/<slug>/strategy/campaigns/<name>.yaml` に「目標KPI・参加媒体と役割・スケジュール・成果の測り方」を記録。**`goal_kpi:`（KPIツリーに実在するノード名）と `channels:`（オーガニック媒体）の2キーは機械検証の対象**なのでこの名前で書く（他は自由記述。形は docs/domain-model.md「ワークスペース検証」。`scripts/lint.py --workspace .` で検証）。
5. **実行は下流の各パックへ**: 実際の制作・投稿は /匠発信 の各手順書（`takumi-sns`・`takumi-content`・`takumi-ownedmedia`・`takumi-email`・`takumi-website`）が担う（変更操作は takumi-start のゲート下・不可逆送出は pre-send-verifier + 承認）。キャンペーンは司令塔として進捗を束ねるだけで、手順を複製しない。
6. **計測を上流へ返す（∞の上り）**: 各媒体の実測を **/匠計測**（procedures/takumi-analytics.md）で取得し outcome-verifier が集計 → 目標KPIノードの進捗を更新 → /匠戦略 の再立案インプットにする。**計測の手段が無い目標KPIは、キャンペーン開始前に /匠計測 で測れるようにする**。
7. **ダッシュボード**: /匠計測 のトップ（ダッシュボード）でキャンペーン進捗・KPIツリーの動きを可視化する。

## 原則

- 1キャンペーン=1目標（KPIツリーの1ノード）。媒体を増やすより、1つの物語で束ねることを優先。
- **集客を増やす前に、何を差し出しているかを見る。** 流入が同じでもオファーを変えれば成果は変わる（→ `skills/offer-design-jp`）。**媒体を足す提案より先に、オファーの摩擦が残っていないかを確認する。**
- **季節要因を施策の成果に数えない。** 山の時期は同じ努力で数字が伸びる。前年同月・競合を含めた比率で切り分ける（→ `skills/demand-timing-jp` §7・`outcome-verifier`）。
- **獲得で終わらせない。** 転換した人がその後どうなるかは **/匠顧客**（takumi-retention）が担う。ゼロ広告費では既存顧客が最大の獲得チャネルであり、**集めた分だけ漏れる設計はキャンペーンの失敗**として扱う。
- **主張は1つ、形は複数**。モダリティごとに言うことを変えない（面がぼやけて包囲網にならない）。骨子は共通、表現だけを媒体・モダリティに最適化する。**その主張は `knowledge/brands/<slug>/strategy/messaging.md` の柱のどれかでなければならない**（どの柱にも紐づかないキャンペーンは「今回だけの思いつき」であり、面を薄くする → `skills/messaging-design-jp`）。
- 費用は使わない。ブースト・出稿・課金導線は組み込まない（ゼロ課金ゲートが遮断）。
- 複数ブランドを運用している場合も、キャンペーンは常にアクティブブランドの区画に閉じる。
