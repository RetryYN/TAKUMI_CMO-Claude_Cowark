# /匠広報 — 他者の場で認知を広げる（takumi-pr）★玄関

`ChannelKind.EARNED`（広報・連携）の実行パック。**自社の場ではなく、他者の場・他者の口**で認知を広げる。

> **なぜこれが要るか**: マーケティングの媒体は **Owned / Earned / Paid** に分かれる。匠CMO は
> **Paid を構造的に持たない**（ゼロ広告費）。Owned は5パックで揃っている。
> **Earned が空いていると、認知を伸ばす手段が自社の場だけに閉じる** — 届く相手が増えない。
>
> **前段**: アクティブブランドを確定する（未確定なら /匠設定）。記録は `knowledge/brands/<slug>/channels/earned/` にスコープされる。
> **主張の正本**: `knowledge/brands/<slug>/strategy/messaging.md`。**外に出す話は必ず柱のどれかに紐づく**（→ `skills/messaging-design-jp`）。

## 大原則

1. **こちらの都合はニュースではない。** 相手の読者にとって何が新しいかを先に言えなければ、打診しない。
2. **相手の場のルールに従う。** 媒体・コミュニティにはそれぞれの作法がある。自社の宣伝文をそのまま持ち込まない。
3. **対価が絡んだら表示義務が生じる**（ステマ規制）。金銭・物品・便宜のいずれかを渡すなら **PR表記が要る**（→ `skills/ad-compliance-jp`）。
4. **送信・投稿・打診の実行は不可逆送出。** `pre-send-verifier` の監査 + **人間承認**を経る。
5. **有料の掲載枠・記事広告・インフルエンサー起用は扱わない**（それは Paid。ゼロ広告費・ゼロ課金ゲート対象）。

## 要望の振り分け（タスク4型）

| 要望の型 | やること | 参照 |
|---|---|---|
| 「プレスリリースを書いて」 | ニュース性の判定 → 起案 → 承認 → 配信 | 下記① |
| 「取材してほしい」「紹介されたい」 | 相手選び → 個別の打診 | 下記② |
| 「他社とコラボしたい」 | 相互に得るものの設計 | 下記③ |
| 「コミュニティを作りたい」 | 目的と役割の設計（作る前に） | 下記④ |

## ① プレスリリース

### まずニュース性を判定する（無いなら出さない）

| 判定 | 質問 |
|---|---|
| **新しさ** | 業界にとって初か、自社にとって初か（後者だけなら弱い） |
| **具体性** | 数字・日付・固有名で言えるか |
| **影響** | 誰の何が変わるのか |
| **今である理由** | なぜこのタイミングか |

**4つとも埋まらないなら出さない。** 「新機能を出しました」だけのリリースは、
配信数を増やすだけで信用を減らす。

### 書き方

- **タイトルで内容が分かる**（32字前後。→ `skills/copywriting`）
- **リード文で結論**（誰が・何を・いつから・誰向けに）
- **数字は実測値のみ**（母数と期間を併記）
- **推測・意気込みを事実の中に混ぜない**（「〜を目指します」は最後に隔離）
- **問い合わせ先を明記**
- `skills/business-writing`（構成）+ `skills/ad-compliance-jp`（最上級表現・保証表現の可否）を通す

## ② 取材・掲載の打診

**一斉送信しない。** 相手ごとに理由を書く（テンプレ臭が最大の失敗要因 → `skills/psych-target-jp`）。

1. **相手を選ぶ**: その媒体・発信者が**実際に何を扱ってきたか**を読む（`docs/parts/deep-research.md`）。
   直近の記事・投稿に触れられないなら、その相手は選んでいないのと同じ
2. **なぜその相手なのかを1〜2行で書く**（相手固有の事実。冒頭2文以内）
3. **相手の負担を減らす**（素材・数字・画像を揃え、確認の手間を先に潰す）
4. **断りやすさを残す**（`skills/business-writing` の依頼メールの型）
5. 送信は `/匠発信` 経由。**不可逆送出のゲート下**

**掲載後**: 掲載先・日付・内容を記録し、`/匠計測` で流入と指名検索の変化を見る。

## ③ パートナー連携（共同企画・相互紹介）

**相互に得るものを先に書く。** 片方だけが得る話は続かない。

| 決めること | 中身 |
|---|---|
| 目的 | どちらの KPIツリーのどのノードを動かすか（**両方書く**） |
| 役割 | 誰が何を作り、誰がどこに出すか |
| 表記 | どちらの名前をどう出すか |
| **金銭の有無** | **発生するなら PR表記の対象**。無償なら無償と明記 |
| 期間と終わり方 | いつまでか、どう終えるか |
| 出さない情報 | 相手から得た非公開情報の扱い |

**相手の顧客リストを受け取らない。** 個人データの移転は同意の問題であり、
安易に受けると取り返しがつかない（個人データが絡む設計は `docs/parts/pre-setup-council.md` の合議に
privacy-auditor を呼ぶ）。

## ④ コミュニティ

**作る前に、なぜ人が来るのかを言えるようにする。** 「囲い込みたい」は運営側の都合で、参加の理由にならない。

1. **参加者が得るもの**を1つに絞る（情報／つながり／承認／先行体験）
2. **運営の工数を先に見積もる**（`docs/parts/capacity-plan.md`）。
   **場は作るより続けるほうが重い。** 続けられないなら作らない
3. **役割を決める**（誰が答えるか・どのくらいの速さで）
4. **やめ方を決めておく**（畳むときに参加者をどうするか）
5. 荒れたときは `/匠危機対応` へ

**発言を勝手に引用しない。** 事例・声として外に出すなら**必ず許諾を取る**。

## 記録と接続（ここまでやって完了）

1. `knowledge/brands/<slug>/channels/earned/<date>-<件名>.md` に、**相手・打診内容・結果**を記録
   （断られた記録も残す — 次に同じ相手へ重複打診しないため）
2. 掲載・共同企画の成果は `/匠計測` で測り、**KPIツリーのノードに紐づける**（∞の上り）
3. 外に出した主張が **messaging.md の柱に紐づいているか**を確認（→ `docs/parts/messaging-audit.md`）

## 禁止・注意

- **有料掲載・記事広告・インフルエンサー起用は扱わない**（Paid。ゼロ課金ゲート対象）
- **対価を伏せた紹介依頼をしない**（ステマ規制違反）
- **一斉送信の打診をしない**（相手ごとの理由が無い打診は、届いても信用を減らす）
- **相手の非公開情報・顧客リストを受け取らない**
- 実在しない実績・数字を書かない（**創作は1件でも致命** → `skills/sales-writing`）
