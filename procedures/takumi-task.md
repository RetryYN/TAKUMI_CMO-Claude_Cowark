定常タスク管理を実行してください。サブコマンド: $ARGUMENTS

## register（デフォルト）— タスクの自動構築

### 1. ヒアリング（足りないものだけ聞く。依頼文から読み取れる項目は確認に留める）

1. **カテゴリー**: SNS媒体 / オウンド / 戦略 / 基盤 / 記録 / 横断（docs/command-registry.md の分類軸）
2. **場所**: どのサイト・媒体・アカウントか（knowledge/sites/ のキー。未登録なら新キーを起こす）
3. **やること**: 手順を自然言語で（1操作=1ステップに分解するのはこちらの仕事）
4. **変動値**: 毎回変わる値（params 化）
5. **周期**: 毎朝/平日/週次など（単発なら schedule なし）
6. **禁止事項・承認したい箇所**: destructive 判定に加えたいものがあれば

### 2. タスクYAML生成

- `templates/task-template.yaml` を骨格に `tasks/<タスク名>.yaml` を生成（タスク名は英語ケバブ）
- **ブラウザ操作を含むタスクの steps 先頭に「knowledge/config/browser.md を読み、優先ブラウザが記録されていれば選択する」interact ステップを標準装備する**（複数 Chrome 接続時の選択待ちで無人実行が停止する実測事故の防止。正本は docs/unattended-ops.md §ブラウザの一意化）
- 送信/公開/投稿/保存を含むステップは **destructive を明示**（Step H で人の承認を必ず通る設計にする）
- `generate_text` にはスキル台帳（docs/command-registry.md）からドメインに合うスキルを割当
  （投稿=content-design+sns-jp、コピー=copywriting 等）
- 同種の文面生成を高頻度で行うタスクなら、あわせて takumi-skillify でのワークスペーススキル化を提案する

### 3. ナレッジの足場

- `knowledge/sites/<place>/` が未整備なら作成し、index.md に「初回実行時に 探索マッピング方式（掘る）でマッピングする（フェーズ①）」と記録

### 4. ループ登録

- `knowledge/config/loops.yaml` に追記（なければ作成）:
  ```yaml
  loops:
    - task: <タスク名>
      domain: <ドメイン>
      cadence: "平日 10:00"
      close_with_dashboard: true
  ```
- **スケジュール登録（2026-07-26 全面改訂 — 規則の正本は `docs/unattended-ops.md` §スケジュールの正本。必ず Read する）**:
  - **匠CMO の定常タスクは Desktop（ローカル）に登録する。** cloud（Routines）は
    **`knowledge/` が見えない**（fresh clone）ので、ブランド区画・戦略・KPIツリー・文体の正本が
    **無い状態で走る** — 記憶が本体のマーケ運用は成立しない。ブラウザ操作も実PCに届かない
  - **AI が登録まで進める。** 「毎朝これやって」と言われたら、**オーナーのUI操作を待たずに登録する**
    （公式: "create a task by describing what you want in any session" / "list, create, edit, and
    pause tasks by asking Claude in any Desktop session"）。**2026-07-26 まで「AI は登録できない」と
    書いていたが誤りだったので削除した**
  - **プロンプトに時刻ガードを1行入れる（必須）**: PC が寝ていた分は**まとめて1回**、実態とずれた時刻に走る
    （公式: "A task scheduled for 9am might run at 11pm"）。例:「**今が12:00を過ぎていたら観測だけ行い、
    投稿・配信はしない**」。**不可逆送出を含むタスクでは特に必須** — 無いと深夜に「おはようございます」が出る
  - **発火プロンプトは短く、`/匠◯◯` を使ってよい**（例:「`/匠計測 今日の作業まとめて`。終わったら
    ダッシュボード更新」）。詳細手順は `tasks/<タスク名>.yaml` に置き発火時に読ませる
  - **登録したら「次回はいつ動くか」を読み上げて確認を取る。** 時刻の解釈は経路で違い、
    ジッターで数分ずれる。**暗算で済ませない**（ズレは後から気づくと、その間ずっと空振りしている）
  - **登録直後に Run now を1回実行し、権限プロンプトで「always allow」を選ぶよう案内する。**
    飛ばすと以後のランが承認待ちで静かに止まる（止まったこと自体に気づけない）
  - 登録前に「**無人運用前チェック**」（`docs/unattended-ops.md`）を実行し、✗ 媒体があれば
    オーナーのログイン揃えを先に依頼する
  - `loops.yaml` には登録済みの日付を記録する（**Run now まで確認できて初めて「登録済み」**）

### 4b. 次回以降どう良くするか（登録して終わりにしない）

**定常タスクは走るたびに自分を直せる** — `update_scheduled_task` MCP ツールで**自分の予定とプロンプトを
書き換えられる**（公式仕様）。生成する YAML には、次の見直し条件を必ず1つ以上入れる:

| 観測 | 直し方 |
|---|---|
| 3回続けて「変化なし」 | **間隔を広げる**（無駄な発火は利用者の注意を削る） |
| 毎回同じ手直しをしている | その手直しを**プロンプトに畳み込む**（→ やり方の記憶） |
| 実行時刻がいつもずれている | **PCが起きている時間に寄せる** |
| 前提が変わった（媒体をやめた等） | 該当部分を**プロンプトから落とす** |

**直したら、何をどう変えたかを1行で報告する。** 黙って予定を変えない
（予定の変更は、利用者の期待を裏切りうる不可逆に近い操作）。記録は `knowledge/logs/` と `loops.yaml`。

**加えて、毎回の実行結果から学びを拾う**: FAIL や手直しが出たら `knowledge/feedback/lessons.md` に
1行残し、**次回のプロンプトに反映する**（→ `procedures/takumi-feedback.md`）。
**同じ手直しを3回したら、それはタスク定義の不足**であって利用者の手間ではない。

### 5. 壁打ち（設計のセカンドオピニオン）

YAML 案を確定する前に、strategy-advisor サブエージェントに (a)タスクYAML案の絶対パス、(b)目的とKPI、(c)関連する knowledge/ のパスを渡して審査させる。VERDICT が GO-WITH-CHANGES / RETHINK なら指摘を検討して反映または理由付きで却下し、採否を YAML のコメントか knowledge/logs/ に1行記録する。

### 6. 確認

生成した YAML とループ登録内容（壁打ちの VERDICT 含む）をユーザーに提示し、修正があれば Edit で反映してから完了報告。

### 7. 以後の実行（このコマンドの仕事ではない）

- 実行は従来どおり **takumi-start** が担う: 「<タスク名>やって」→ takumi-start が `tasks/<タスク名>.yaml` を読み、steps を実行計画の正として A〜K を回す（destructive ステップは H で承認）
- ダッシュボードは `tasks/*.yaml` + `loops.yaml` を読んでタスク一覧・タブ・次回実行を自動反映する

## list

`tasks/*.yaml` と `knowledge/config/loops.yaml` を突き合わせ、表で表示: タスク / ドメイン / 場所 / 周期 / 最終実行（knowledge/logs/ から）/ 状態

## remove <タスク名>

`tasks/<タスク名>.yaml` と loops.yaml の該当行を削除（**knowledge/sites/ の蓄積は消さない**）。削除前に対象を提示して確認を取る。
